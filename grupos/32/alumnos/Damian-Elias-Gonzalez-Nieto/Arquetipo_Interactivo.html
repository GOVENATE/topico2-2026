Objetivo del arquetipo
Explicar por qué reaccionamos de más cuando los resultados tardan en aparecer.
Problema típico
Se aplican correcciones repetidas antes de que la primera tenga tiempo de funcionar.
Consecuencia
Se generan sobreajustes, inestabilidad o frustración.

Ideas clave del arquetipo

DescripciónRespuesta a una meta con realimentación demorada.
Advertencia“Creíamos estar en equilibrio, pero nos excedimos”.
PrincipioEn sistemas lentos, la agresividad crea inestabilidad.
ClaveSer paciente o acelerar la capacidad de respuesta del sistema.

¿Qué es?

Compensación entre proceso y demora es un arquetipo sistémico que aparece cuando una persona, grupo u organización intenta corregir una situación, pero los resultados tardan en verse. Como no se percibe el cambio de inmediato, se toman más acciones correctivas de las necesarias o se abandona la estrategia antes de tiempo.

En palabras simples: corriges algo, pero como el sistema responde lento, piensas que no funcionó y vuelves a corregir… hasta descontrolarlo.

Porque solemos evaluar el sistema con base en resultados inmediatos. Cuando no vemos mejoras rápidas, asumimos que la acción no sirve, aunque el sistema todavía esté procesando el cambio.
La prisa, la presión por resultados, la mala lectura de métricas y la falta de comprensión sobre los tiempos reales de respuesta.
Diseñando indicadores adecuados, definiendo ventanas de observación realistas, y diferenciando entre una respuesta lenta y una respuesta inexistente.
Aplicación

¿Cómo se aplica este arquetipo?

1) Identificar la meta

Primero se define qué se quiere equilibrar o mejorar: rendimiento, calidad, tiempos de entrega, satisfacción del usuario, etc.

2) Detectar la acción correctiva

Se observa qué medidas se toman para corregir el problema: aumentar recursos, cambiar procesos, reconfigurar un sistema, capacitar personas o corregir código.

3) Reconocer la demora

Aquí está la parte más importante: ¿cuánto tarda realmente la corrección en mostrar resultados? Si no se sabe, se puede sobreajustar el sistema.

  1. Medir el estado actual: usar indicadores reales, no suposiciones.
  2. Aplicar una corrección razonable: evitar cambios impulsivos o extremos.
  3. Esperar el tiempo de respuesta del sistema: respetar la demora.
  4. Volver a medir: comparar datos antes y después.
  5. Ajustar con base en evidencia: no con ansiedad o presión.
Mega ejemplo del área de informática

Tipo collage: plataforma web universitaria con lentitud

Ejemplo pensado para el área de informática: una plataforma web usada por estudiantes comienza a ponerse lenta en épocas de inscripción y entrega de tareas.

Escenario central

Una aplicación web universitaria presenta tiempos de respuesta altos. El equipo de soporte empieza a recibir quejas, y el área técnica intenta corregir el problema rápidamente.

¿Qué es en este caso?

El equipo quiere mejorar el rendimiento, pero cada optimización tarda tiempo en desplegarse, monitorearse y reflejarse en métricas reales.

  • Meta: bajar el tiempo de respuesta.
  • Condición real: el sistema sigue lento.
  • Acción correctiva: optimizar base de datos o escalar servidores.

Aplicación

Se aplica el arquetipo para entender que no conviene lanzar correcciones en cadena sin esperar evidencia del efecto de cada una.

  • Se mide antes de intervenir.
  • Se aplica una mejora por iteración.
  • Se monitorea con una ventana de tiempo definida.

Demora

La mejora no se ve al instante porque:

  • El despliegue tarda.
  • La caché tarda en estabilizarse.
  • Las métricas requieren tráfico suficiente para validarse.
  • El horario pico todavía no termina.

Error común

Como no se ven resultados en 15 minutos, el equipo:

  • vuelve a tocar el servidor,
  • cambia parámetros de la base de datos,
  • aumenta recursos de forma exagerada,
  • o deshace una mejora que sí iba a funcionar.

Resultado final

El sistema entra en inestabilidad: suben los costos, se mezclan cambios, se vuelve difícil saber qué funcionó y qué no, y el problema puede empeorar.

  • Más complejidad.
  • Mayor riesgo de fallos.
  • Menor claridad para diagnosticar.

Buena práctica

Aplicar correcciones controladas y esperar la respuesta del sistema.

  • Definir hipótesis.
  • Usar métricas base.
  • Monitorear por periodos reales.
  • Documentar cada cambio.

Ejemplo redactado

Ejemplo: En una plataforma escolar, el equipo detecta lentitud y decide optimizar consultas SQL. Como en una hora no cambia mucho la percepción de los usuarios, agregan servidores y cambian la configuración del balanceador. Horas después el sistema responde de manera irregular y es difícil identificar la causa. El problema no era la falta de acción, sino no respetar la demora natural entre la corrección y sus efectos.

Conclusión breve

Este arquetipo enseña que no todo problema debe corregirse con rapidez extrema. En informática, muchas mejoras requieren tiempo para mostrar resultados. Si el equipo desconoce esa demora, puede sobreajustar el sistema y empeorar lo que quería resolver.
