Actividad 05 · Código limpio

Código limpio: escribir para que otro lo entienda

Juan Diego Olvera Medina · LATI, 9.º semestre · Resumen y mapa conceptual de Clean Code, de Robert C. Martin

La idea central

Robert C. Martin parte de una observación incómoda: el código se lee muchas más veces de las que se escribe. Cada vez que alguien abre un archivo para corregir un error o agregar una función, paga el costo de entender lo que escribió otra persona (o uno mismo hace seis meses). El código limpio es el que reduce ese costo. No basta con que funcione; tiene que poder leerse, cambiarse y probarse sin miedo.

"Cualquier tonto puede escribir código que una computadora entienda. Los buenos programadores escriben código que los humanos pueden entender." (Martin Fowler, citado en el libro)

Las reglas que más pesan

1. Nombres que revelan la intención

Un nombre debe responder por qué existe algo, qué hace y cómo se usa. d no dice nada; diasDesdeUltimoPago lo dice todo. Si un nombre necesita un comentario para explicarse, el nombre está mal.

2. Funciones pequeñas que hacen una sola cosa

Una función debe hacer una cosa, hacerla bien y hacer solo esa. Si se puede extraer otra función con un nombre que no sea una simple repetición, la función original hacía más de una cosa. Menos argumentos es mejor: cero es ideal, tres ya es sospechoso.

3. Comentarios: el último recurso

Un comentario suele ser la disculpa por un código que no se explica solo. Los comentarios mienten con el tiempo porque el código cambia y ellos no. Valen para explicar una intención o advertir una consecuencia, no para describir lo que el código ya dice.

4. Formato y orden

El código se lee de arriba hacia abajo como un periódico: lo importante primero y los detalles después. Las funciones que se llaman entre sí van cerca, y los conceptos relacionados quedan juntos.

5. Manejo de errores sin ensuciar la lógica

Usar excepciones en lugar de códigos de error, no regresar null y no pasar null como argumento. El manejo de errores es una responsabilidad aparte y no debe esconder lo que la función realmente hace.

6. Pruebas limpias

Las pruebas son tan importantes como el código de producción. Siguen las reglas F.I.R.S.T.: rápidas, independientes, repetibles, que validan solas y escritas a tiempo. Sin pruebas, cualquier cambio da miedo y el código se pudre.

7. La regla del Boy Scout

Deja el código un poco más limpio de lo que lo encontraste. No hace falta una gran reescritura: renombrar una variable o partir una función larga, cada vez que pasas por ahí, evita que el sistema se degrade.

Mapa conceptual

Relación con la administración de las TI

En un proyecto de TI el código es uno de los activos principales. El código sucio se convierte en deuda técnica: cada cambio tarda más, cuesta más y rompe más cosas. Conocer estas reglas ayuda a quien administra un proyecto a pedir, revisar y estimar mejor el trabajo de un equipo de desarrollo.
